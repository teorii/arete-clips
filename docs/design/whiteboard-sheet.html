The Whiteboard Sheet

Two diagrams, built to be reproduced rather than admired. The target is both on a blank page in under four minutes without hesitating, because hesitating in front of an interviewer costs more than getting a box slightly wrong.

01

The system

The sequence, in words

Say these out loud while you draw. The numbers match the badges.

1
Client calls POST /clips. Sends metadata: game, duration, size. The API holds the session token, so this is the step that knows who the user is.client to API
2
API inserts the clip row, then mints presigned URLs with your cloud credentials and returns the clip id, public slug, and those URLs.API to Postgres, then back to client
3
Client PUTs bytes straight to object storage. 480p proxy first so the link is live in about four seconds, source following in the background, chunked and resumable. Then POST /clips/:id/complete.client to object storage
4
Object storage emits an object-created event onto the job queue. Nothing polls.object storage to queue
5
A transcode worker picks up the job. Fresh clips take priority over backfill.queue to workers
6
Worker writes renditions back to storage and updates the clip's status in Postgres. Idempotent on clip id, so a retry is safe.workers to storage and Postgres
7
A viewer opens the link. Their browser calls the API with the public slug. The API reads Postgres and returns metadata plus a CDN playback URL, signed if the clip is private.viewer to API
8
The player requests video from the CDN, never from your API and never from object storage directly.viewer to CDN
9
On a cache miss the CDN pulls from object storage, its origin, then serves everyone after that from the edge.CDN to object storage
Draw order on a real whiteboard

Client far left. API and Postgres along the top. Object storage directly right of the client. Queue and workers right of that. CDN and viewer far right. Event pipeline as one long box across the bottom, added last. Boxes first, arrows second. If you start with arrows the layout fights you and you will run out of room.

02

The schema

What to say about each choice

  • id is a UUIDv7, public_slug is separate. Time-ordered ids index well; a random UUID as primary key wrecks insert locality. The slug is what appears in the URL, so it is short and not enumerable.
  • Two timestamps. captured_at comes from a clock you do not control and can lag by days. uploaded_at is yours. Sort by the first, trust the second.
  • Renditions are a table, not columns. This is what makes lazy transcoding possible without a migration every time you add a size.
  • The partial index (where deleted_at is null) keeps soft-deleted rows out of the index entirely. This is the specific thing you would give up on MySQL.
  • Monthly partitions turn retention into DROP PARTITION instead of deleting a hundred million rows.
If they ask you to write it out

You do not need exact syntax. Draw the boxes, name the columns, say the five bullets above. An interviewer asking for a schema wants to see that your entities match your access patterns, not that you remember whether it is timestamptz or timestamp with time zone. Those are the same thing anyway.

03

How to actually drill this

Reading a diagram five times does almost nothing. Reproducing it once does more than reading it ten times. So:

  1. Round one, copy it. Look at the system diagram and redraw it on paper. You are learning the spatial layout, not testing yourself yet.
  2. Round two, boxes only, from memory. Nine boxes. If you miss one, look, then start again from a blank page rather than patching it in.
  3. Round three, add arrows and say the nine steps out loud as you draw each one. Out loud matters, because the interview is spoken and you need the words attached to the strokes.
  4. Round four, the schema. Four tables, then the relationships, then the dashed events box last.
  5. Round five, both, timed. Four minutes for the pair. Hit that and you will never be the candidate staring at a blank whiteboard.
The two you cannot get wrong

The fork at step 3 (metadata to the API, bytes past it to storage) and steps 8 and 9 (viewer to CDN to object storage). Those are the exact two places you got tangled in the mock, and they are the same principle pointing in opposite directions: your application tier moves metadata, never video. Get those right and the rest is ordinary infrastructure.
