The Medal Question

Design a gameplay clip capture service. Content originates on a stranger's gaming PC, arrives constantly, and is watched almost never. That inverts nearly every instinct a video system design answer normally runs on.

01

Understand the problem

What is a gameplay clip service?

Medal is a desktop application that continuously records gameplay in the background. When something good happens, the player presses a hotkey and the last thirty seconds are saved, trimmed, uploaded, and turned into a link they can paste into Discord before the next round starts.

The critical framing, and the thing to establish in your first two minutes: the content originates on the user's machine, not on your infrastructure. That single fact is what separates this from every video system design question you have practiced. It is worth explicitly naming the alternative you are not building.

Functional requirements

Core requirements

  1. Users should be able to save the last N seconds of gameplay by pressing a hotkey.
  2. Users should be able to trim a clip before publishing it.
  3. Users should be able to upload a clip and get a shareable link.
  4. Users should be able to watch a clip from that link.
  5. Users should be able to browse and delete clips in their own library.
Below the line

Out of scope

  1. Social graph: following, friends feeds, notifications.
  2. Comments, reactions, and content moderation.
  3. Live streaming.
  4. Multi-clip editing, montages, music overlays.
  5. Console and mobile capture.
  6. Monetization and creator payouts.

Say the below-the-line list out loud rather than silently ignoring it. Naming what you are cutting is how the interviewer knows you cut it deliberately.

Non-functional requirements

This is where this problem stops resembling a normal video question, so slow down here. Quantify everything.

Core requirements

  1. The system should cost the player less than about 5% of their framerate while capturing. This is not a nice-to-have. A tool that drops a competitive shooter from 144 to 110 fps gets uninstalled, and no other feature compensates.
  2. The system should get from hotkey press to shareable link in under 30 seconds at p50, on a typical residential connection. Time-to-link is the product's north-star metric.
  3. Uploads should be resumable across app crashes, reboots, and multi-day offline gaps.
  4. The system should prioritize durability over availability for clips. A clip that is briefly unviewable is annoying; a clip that is lost is gone forever, and the user was there for the moment.
  5. The system should stay economical at a very poor watch rate. Assume most clips are viewed zero or one times, ever.
  6. Scale target: 10M MAU, 2M DAU, roughly 1.2M clips/day, roughly 48 TB/day of ingest.
Below the line

Out of scope

  1. Strong consistency on view counts and social counters.
  2. Sub-100ms playback start worldwide.
  3. Multi-region active-active.
  4. Full compliance treatment, though consent for incidentally captured voice deserves one sentence.
The move that separates you

Most candidates write non-functional requirements that would fit any system: "highly available, low latency, scalable." Requirement 1 above could not appear in any other problem, and it constrains the design more than the other five combined. Land it explicitly: "The unusual constraint here is that our software runs on the user's GPU while they are playing a game, so our performance budget is measured in their framerate. I want to design around that first."

02

The set up

Planning the approach

Say your plan before you draw: entities, then API, then build the high-level design one functional requirement at a time, then go deep where they want. Announcing the sequence costs fifteen seconds and makes the rest of the hour legible.

One judgment call worth stating: you intend to spend meaningful time on the client. In most system design questions the client is a caller. Here it is the majority of the difficulty, and if you spend the whole hour to the right of it you will have answered a different question than the one asked.

Defining the core entities

  • User — account, tier (free or paid), storage quota.
  • Clip — the central entity. Owner, game, capture time, duration, status, visibility, and the capture metadata that tells you how the recording actually went.
  • Rendition — one encoded output of a clip at a given resolution. Deliberately a separate entity, because renditions are generated lazily and a clip may have only one for a long time.
  • Game — reference data mapping a running process to a known title.
  • ClipEvent — behavioral events. Worth naming as an entity and immediately saying it does not live in your primary database. It goes to the event pipeline.

The API

// Create the record and get somewhere to put the bytes.
POST /clips
  { gameId, durationMs, capturedAt, sourceBytes, captureMeta }
  -> { clipId, publicSlug, uploadUrls: [...] }

// Client confirms all parts landed; server enqueues processing.
POST /clips/:clipId/complete
  { parts: [{ partNumber, etag }] }

// Public read, cacheable, usually unauthenticated.
GET /clips/:publicSlug
  -> { clip, renditions: [...], playbackUrl }

// The dominant authenticated read. Keyset pagination, not OFFSET.
GET /users/me/clips?cursor=&limit=30

// Trim is NOT here: it happens on the client before upload.
// Server-side re-trim is a v2 feature that fights the retention
// policy, since it means keeping the source instead of tiering it.
PATCH  /clips/:clipId   { title?, visibility? }
DELETE /clips/:clipId
Point at this yourself

Notice that no endpoint accepts video bytes. The client PUTs directly to object storage using presigned URLs, and your API only ever moves metadata. Proxying 40 MB of video through your application tier is the single most common mistake on this question, so call out that you have avoided it rather than hoping it is noticed.

03

High-level design

Background: how gameplay capture works

You do not need video expertise, but you do need these terms used correctly. If you have no video background, this is the section to over-prepare.

codec vs. container

A codec (H.264, HEVC, AV1) compresses the pixels. A container (MP4, MKV) wraps video, audio, and metadata tracks together. Capture to H.264 in MP4 for universal playback.

hardware encoder

Dedicated silicon on the GPU: NVENC on NVIDIA, Quick Sync on Intel, AMF on AMD. It does not compete with the game for shader cores. This is why the product can exist.

ring buffer

A fixed-size circular buffer the client encodes into continuously, overwriting the oldest data. The hotkey does not start recording; it decides to keep what was already recorded.

I-frame, P-frame, GOP

An I-frame is a complete image; P-frames store only differences from earlier frames. A GOP runs from one I-frame to the next, typically about 2 seconds.

remux vs. transcode

Remux rewrites the container without touching compressed video: instant and lossless. Transcode decodes and re-encodes: slow, lossy, expensive. Say "remux" whenever you can avoid the latter.

ABR ladder

Multiple encodes of one clip at different resolutions so the player can adapt to bandwidth. The lever in this problem is refusing to build the whole ladder up front.

bitrate math

Bytes = bitrate × seconds / 8. 1080p60 gameplay wants 8 to 12 Mbps because fast motion compresses badly, so 30 seconds is roughly 40 MB.

presigned multipart upload

Short-lived signed URLs let the client upload chunks directly to object storage, in parallel and resumably, without touching your servers.

1) Users can save the last N seconds of gameplay

Start here, and note something worth saying aloud: this first requirement is satisfied entirely on the client. No server appears in the design yet. The client continuously acquires rendered frames, encodes them with the GPU's hardware encoder, and writes the compressed output into a ring buffer. A hotkey flushes the buffer to a local file.

Two decisions to volunteer while you are here:

  • Back the ring buffer with disk, not just RAM. Games crash and GPU drivers reset, and the thirty seconds a player most wants to keep are very often the thirty seconds right before something went wrong. A pure RAM buffer loses exactly the footage with the highest save intent. At 10 Mbps the write load is trivial.
  • Keep audio on separate tracks. Game audio, microphone, and voice chat as distinct tracks rather than a premix. It is free at capture time and irreversible if skipped, and it unlocks the most requested feature in this category: muting your own microphone after you have heard what you said.

2) Users can trim a clip

Trim on the client, before upload. It gives instant feedback and means fewer bytes on the wire. The mechanism is worth one diagram, because every trimming follow-up resolves to it.

3) Users can upload a clip and get a link

The client calls POST /clips, receives a clip id plus presigned part URLs, uploads chunks directly to object storage, then calls complete. A storage event enqueues processing. Components added: API service, metadata database, object storage, job queue.

4) Users can watch a clip from that link

Two separate moments, worth keeping distinct. When the transcode worker runs (before anyone watches) it writes rendition files to object storage, sets the rendition row to ready, and moves the clip's status to ready. When a viewer actually plays the clip, nothing in the database changes synchronously: the player reads from the CDN with a signed URL, and the view becomes an event that updates view_count in batches later. A viral clip must never turn into a write storm on the clips table. Components added: transcode workers, CDN.

The important decision, which anticipates deep dive 3: produce one shareable rendition on ingest and generate the rest lazily on first playback. Most clips never get a first playback.

5) Users can browse their library

An indexed read against the metadata database, keyset paginated. Components added: read replicas. This is also where the schema question usually arrives, so have this ready:

-- Time-ordered ids: index locality, rough creation order for free,
-- and nothing enumerable sitting in a public share URL.
create table clips (
  id            uuid primary key,        -- UUIDv7
  public_slug   text unique not null,    -- base62, what the URL shows
  owner_id      uuid not null references users(id),
  game_id       int  references games(id), -- null = unrecognized game
  status        clip_status not null,     -- pending_upload, uploaded, ready, failed
  visibility    visibility  not null default 'private',
  trigger_type  trigger_type not null,    -- hotkey | auto | manual
  duration_ms   int not null,
  captured_at   timestamptz not null,     -- client clock: may lag days, or lie
  uploaded_at   timestamptz,               -- server clock: the trustworthy one
  storage_tier  storage_tier not null default 'hot',
  capture_meta  jsonb,                     -- encoder, gpu, fps impact, dropped frames
  view_count    bigint not null default 0, -- denormalized from the event stream
  deleted_at    timestamptz
) partition by range (captured_at);      -- monthly: expiry becomes DROP PARTITION

-- The dominant read, served by one composite index.
create index on clips (owner_id, captured_at desc, id desc)
  where deleted_at is null;

-- Separate table, because we transcode lazily. As columns on clips,
-- adding a rendition later would be a migration.
create table clip_renditions (
  clip_id     uuid not null references clips(id) on delete cascade,
  label       text not null,             -- '720p', '1080p', 'thumb'
  status      rendition_status not null, -- absent | queued | ready | failed
  storage_key text,                       -- key, not URL: domains and signing change
  bytes       bigint,
  primary key (clip_id, label)
);
  • Two timestamps, deliberately. The client may have been offline for days, so capture time and upload time genuinely differ. Sort by captured_at because that is what the user remembers, but treat it as untrusted input from a clock you do not control and clamp bogus values against uploaded_at.
  • Keyset pagination, never OFFSET. Users with ten thousand clips exist, and OFFSET degrades linearly for exactly the heavy users you least want to annoy.
  • Views are denormalized. A row per view in your primary database is the wrong shape. Views go to the event pipeline; the counter is a read-optimized copy updated in batches.
The datastore answer, and why it is the brave one

Postgres. One primary, read replicas, partitioned monthly. Candidates reach for Cassandra or DynamoDB reflexively whenever "video" appears, pattern-matching to scale that is not present. Point at your own estimate: 14 writes per second and a few hundred million rows a year sits comfortably in one well-indexed relational database, and you keep transactions and joins while the product is still figuring out what it is. Then name your own trigger for revisiting it: when index maintenance shows up in write latency. Choosing the boring option and stating the condition under which you would abandon it reads as judgment.

04

Potential deep dives

1) How do we capture 60fps gameplay without costing the player framerate?

The defining question of the problem. If you go deep on only one thing, go deep here.

BadScreen-capture the desktop, encode on the CPU
Approach
Grab the framebuffer with a general screen capture API, hand frames to a software encoder like x264.
Challenges
Software encoding at 1080p60 costs 15 to 30% of framerate, which violates the one requirement the product cannot violate. You are also competing with the game for CPU during exactly the moments it needs the most.
GoodUse the GPU's hardware encoder
Approach
Route frames to NVENC, Quick Sync, or AMF instead of the CPU. Dedicated silicon, no contention for shader cores.
Challenges
Correct, but incomplete. If you copy each frame to system RAM before handing it to the encoder, you have created a 500 MB/s transfer across the PCIe bus and most of the cost you were trying to avoid comes right back.
GreatKeep the frame GPU-resident end to end
Approach
Capture into a GPU texture and feed it straight to the hardware encoder. Only the compressed stream, about 1.25 MB/s, ever crosses into system memory.
Why it wins
Roughly 400x less data movement. The line to say: "the expensive part is the copy, not the encode."

2) How do we get 40 MB off a residential uplink without ruining the game?

BadPOST the file to the API server
Approach
Client uploads the clip to your application tier, which writes it to storage.
Challenges
Your servers now carry 48 TB/day of video they do not need to touch. A dropped connection at 90% restarts from zero, and on a flaky connection it may never finish at all.
GoodPresigned multipart, direct to object storage
Approach
Server issues signed part URLs; client uploads 5 to 8 MB chunks in parallel, persisting progress to local disk so a crash or reboot resumes rather than restarts.
Challenges
Solves reliability but not experience. A saturated uplink adds latency to the match the player is still in, and they wait the full upload before they can share.
GreatProxy-first upload with bandwidth-aware scheduling
Approach
Encode a small 480p proxy on the client (the hardware encoder is right there and idle), upload that first so the share link is live in a few seconds, then upload the source in the background. Throttle to a fraction of measured uplink while a game is in the foreground, go full speed once they alt-tab.
Why it wins
It attacks the actual product metric. Time-to-link stops being bounded by the source upload, and the player never loses a fight because their last clip was uploading.

3) How do we avoid going bankrupt on storage?

Do the arithmetic out loud first, because the conclusion drives everything after it.

BadFull ABR ladder on ingest, keep everything forever
Challenges
You pay to transcode and store four renditions of clips that, in the majority of cases, nobody will ever open. Cost grows monotonically and the free tier becomes unviable.
GoodLifecycle rules and storage tiering
Approach
Hot for 7 days, infrequent access to 90, then archive. Standard object-storage lifecycle policies.
Challenges
Helps, but you are still paying to generate renditions nobody requested, and a flat timer deletes a treasured clip as readily as a dud.
GreatLazy transcode, engagement-driven retention, time-partitioned metadata
Approach
One rendition on ingest, the rest generated on first playback and then cached. Retention driven by actual engagement rather than a timer. Source kept only for paid tiers. Content-hash dedup for re-uploaded viral clips. And because clips is partitioned by month, expiry is a partition drop rather than a mass delete.
Why it wins
If most clips are never watched, lazy transcoding removes most of the transcode bill by construction, and the schema makes the retention policy cheap to actually execute.

4) How do we operate a client on hardware we do not control?

Not a bad/good/great, but the area where shipped-desktop-software experience shows. Naming two or three of these is a strong signal.

  • Hardware you did not choose. Some users have no hardware encoder. Some have three-year-old drivers. Laptops commonly have two GPUs and the game may be rendering on the one you are not capturing from. You need a capability probe at install and a defined degradation path, including telling a user honestly when their machine cannot run this well.
  • Anti-cheat. Injecting into a game's render loop is behaviorally identical to what a cheat does. This is a business relationship as much as an engineering one: per-title handling, allowlisting, and actual conversations with vendors.
  • You cannot hotfix. A backend bug is one deploy from fixed; a client bug is in the wild until users update, and some never will. Staged rollout by cohort, a server-controlled kill switch for the capture path, and server-driven config wherever possible.
  • Observability is the client's job. You cannot attach a profiler to a stranger's gaming session. If the client does not self-report encoder failures, dropped frames, measured framerate impact, and upload success, you will learn that a driver update broke capture on a whole GPU family from your reviews.

5) How do we collect the data that makes auto-detection possible?

Given that this role pairs the design round with an AI round, expect this one. The events worth capturing, and what each is really for:

  • clip_trimmed with original and final in/out points. The valuable one. A user who saves 60 seconds and trims to 9 has hand-labeled exactly where the interesting moment was, for free, without being asked.
  • clip_viewed with watch percentage. Watch-through rate is your quality label.
  • clip_shared and clip_deleted. Deletion within a minute of creation is a strong negative signal.
  • Capture health and pipeline latency, which protect the two requirements the product rests on.
The flywheel, stated plainly

Capture generously, let the user trim, record where they trimmed. Trim boundaries plus watch-through rates give you a labeled dataset of what a good gaming moment looks like, with no annotation budget and no labeling team. Train on it and auto-detection improves, so users trim less, so capture can be more generous. Also say where detection runs: on the client, over frames you already hold. Uploading video in order to decide whether it was worth uploading inverts the entire cost structure.

One sentence on consent

Gameplay clips capture Discord audio, other players' voices, and whatever else is on screen. That is a real requirement rather than a compliance footnote, and it sharpens the moment you propose retaining clips to train models on.

Final design

Additional deep dives you might consider

  • Deduplicating the same viral clip re-uploaded by thousands of users, by content hash.
  • Cold start for a newly released game with no detection heuristics yet.
  • Thumbnail and sprite-sheet generation for scrub previews.
  • Abuse and moderation on public clips, given that you host user video.
  • Quota enforcement and reconciling a denormalized storage_used_bytes that will drift.
  • Sweeping clips stranded in pending_upload by a client that crashed between the hotkey and the first byte.

05

What is expected at each level

Mid-level

You are here

Breadth over depth. You are expected to produce a complete, working end-to-end design and to follow the interviewer competently into one or two deep dives. They will drive; you are not penalized for that.

  • Get to a coherent design covering all five functional requirements without stalling.
  • Know that capture is client-side and be able to say why that changes things, even if you cannot go three levels deep on encoders.
  • Do the estimation and reach the storage conclusion.
  • Do not need to be told that video bytes should not flow through your API tier.
  • The bar you can clear with two days of prep: know the hardware encoder exists and why it matters, and know that lazy transcoding is the cost lever. Those two facts carry most of the signal.

Senior

Depth, self-directed. You are expected to identify the hard parts yourself rather than waiting to be pointed at them.

  • Volunteer the framerate constraint before being asked, and design around it.
  • Raise cost unprompted and connect it to concrete mechanisms (lazy transcode, partition-based expiry).
  • Defend Postgres over a distributed store using your own QPS number, and name the condition that would change your mind.
  • Handle failure modes without prompting: crashed uploads, orphaned records, stuck transcodes.

Staff+

Scoping and organizational judgment. You are expected to reframe the problem, not just solve the stated one.

  • Identify that the client is the product and the backend is largely commodity, then allocate the hour accordingly.
  • Talk about rollout risk, kill switches, and anti-cheat as a vendor relationship rather than a technical detail.
  • Connect the event pipeline to the ML roadmap, and articulate the flywheel as a strategy rather than a feature.
  • Say what you would build first and what you would deliberately not build for a year.

Appendix 1

The 30-minute AI prototyping round

Not part of the breakdown format, but it is half your Wednesday. You are scored on how you drive the tool, not on how much it produces.

Before the call

  • Have a warm scaffold. A repo that already boots, dependencies installed, dev server confirmed running. Six of your thirty minutes spent on project init is a self-inflicted wound.
  • Confirm the rules today, not Wednesday morning: your machine or theirs, your tools or a prescribed one, screen share or shared editor.
  • Pick a stack you know cold, not the most impressive one. You need to spot bad generated code in seconds.

During

  • Spend the first two minutes not coding. State the vertical slice, what you are cutting, and what "done" looks like at minute 30.
  • Vertical slice, never horizontal. Load a video, set in and out points, produce a trimmed output. Not auth, feed, profile, and settings all half-built.
  • Narrate your prompting. Why that context, why that scope constraint, why you are rejecting that output. The reasoning is the artifact being evaluated.
  • Never let the agent run in silence. Two minutes of dead air is the worst available use of the clock.
  • Read the diff before accepting it, out loud. The failure they are screening for is accepting whatever the model emitted without understanding it.
  • Know when to stop prompting and type. If the agent misses the same thing twice, write it yourself.
  • Hard stop at minute 20. Stop adding, start making what exists actually run.
Likely prompts, given the company

A clip trimmer with in and out points over an HTML5 video element. A clip grid with thumbnails. A "score this clip" tool calling a model over frames or a transcript. A rolling buffer demo in the browser using MediaRecorder. Build a throwaway version of one tonight; the muscle memory transfers even if the actual prompt differs.
